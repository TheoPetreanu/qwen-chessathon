## Design

A magic-bitboard engine compiled with numba. `python-chess` is used ONLY to
parse the incoming FEN and to legality-check the move before returning it; it
never appears in the search. That is the whole point: python-chess in the search
caps you near 30-50k nodes/sec (depth 6-7 on one core), which is where the
leaderboard sits. This engine does 1.0-1.3M nodes/sec, depth 15-23.

Measured: `baseline/agent.py` (a competent python-chess alpha-beta with TT,
killers, qsearch, null move, LMR) runs at 28-36 knps. ~35x gap.

Layout: `engine/` = source of truth, `build/` = copy that gets zipped,
`baseline/` = test opponent, `tests/`, `tools/gen_magics.py` (regenerates magic
constants, fixed seed).

## TWO INVARIANTS — do not break these

1. **Bitboards are `uint64`, never `int64`.** Magic lookups, the de Bruijn
   bitscan and SWAR popcount all rely on multiplication wrapping mod 2^64. On
   int64 that is signed overflow, which numba emits as LLVM `mul nsw` =
   undefined behaviour, and LLVM folds comparisons on the result to poison.
   Observed symptom: a value equal to 1 satisfying BOTH `w >= 2` and `w == 1`,
   which silently disabled all check-evasion generation. It reproduces
   inconsistently, so tests can pass and the bug still ships as an illegal move.
   Rule: bitboards and shift counts are uint64, indices and scores are int64,
   and the two never meet in one arithmetic expression (numba promotes mixed
   uint64/int64 to float64). The zobrist key lives in its own uint64[1] array
   because `st` is int64[5].

2. **Steady-state time spend must stay strictly BELOW the increment.** An
   earlier version flagged because it had a fixed floor (0.75 x 500ms) larger
   than the real increment, draining the clock regardless of base time. Current
   budget: `0.80*inc + usable/28`, hard `min(2.5*soft, 20% of usable)`. The
   increment is inferred each move from `new_clock - (old_clock - spent)`, which
   also absorbs referee overhead we are charged but cannot see. Do not hardcode
   it.

Also: `MAX_SEARCH_PLY = 100` is a hard cap. Check extensions can lengthen a
forcing line without bound and the stacks are fixed size with numba bounds
checking OFF, so overrunning them corrupts memory rather than raising.

## Verified

- Perft exact on startpos, kiwipete, positions 3/4/4b/5/6, en-passant and
  promotion positions. `tests\test_perft.py`, 0 failures on this machine.
- 54,289 positions from 400 random games cross-checked move-for-move against
  python-chess incl. make/unmake restore and incremental zobrist
  (`tests\test_stress.py`).
- Eval exactly colour-symmetric; SEE matches classic cases (`tests\test_eval.py`).
- JIT compile / full init: the "6.8s" figure recorded here earlier was wrong
  and has been corrected (2026-09-09). Real, completed competition games
  (25-game CSV, rounds 46-70) show `init_s` 36.6-49.0s, mean 39.9s -- every one
  finished normally, none failed on init. A clean dev-machine measurement
  matches this (~49s). Still comfortably inside the 90s budget (worst observed
  case leaves ~41s margin), but treat 90s as having ~40-50s of real margin,
  not ~83s -- don't assume the old figure when reasoning about init-time risk
  for future changes (e.g. loading Syzygy tables, an opening book).

## NOT verified

**There is no measured Elo number.** Node rate, depth and correctness are

## Rules

Pure Python source only. No native binaries, no third-party engine or port of
one, no shipped database of another engine's moves/evals, no network. Magic
constants are generated by our own script with a fixed seed, not lifted.

## Testing methodology

Before running ANY match, read METHODOLOGY.md in this folder. It covers core
count, worker count, wall-clock cost per time control, and the statistical
power rule: never adopt a change whose measured effect is inside its own error
bar. 24-game matches cannot resolve anything under ~100 Elo.
